================================================================
MISSION
================================================================

Build a standalone local CLI agent that investigates intermittent Chrome-based web issues.

The agent:
- Accepts reported intermittent Chrome web issues from authorized users
- Converts them into structured flows and ranked experiments
- Executes approved experiments in Playwright with deterministic evidence capture
- Normalizes and redacts evidence deterministically
- Uses DeepSeek to interpret, prioritize, cluster, compare, and explain
- Produces minimized reproductions, passing controls, and Jira-ready reports
- Keeps humans in control at three approval gates

The agent is not a generic test generator, log viewer, session recorder, or replacement for QA, developers, or observability tooling. It investigates a defined class of issues: Chrome desktop and Chrome mobile-emulated web, reproducible at least occasionally, observable from the browser and client boundary, in authorized test environments.

GOVERNING PRINCIPLE
================================================================

Playwright produces evidence. Deterministic software normalizes and measures evidence. DeepSeek interprets and prioritizes evidence. Humans authorize consequential transitions.

This sentence must appear verbatim in CLAUDE.md, docs/architecture/overview.md, and every ADR that touches execution, evidence, or AI.

NON-NEGOTIABLE PRINCIPLES
================================================================

- Browser execution and evidence capture are deterministic.
- DeepSeek is never in the execution loop.
- Every AI output is untrusted until schema-validated and reference-validated.
- Every analytical claim carries explicit, validated evidence references.

- Every AI flow has an explicit tool allowlist and a bounded budget.

- Confirmed root cause requires approved direct evidence. A passing control supports a trigger hypothesis, not a root-cause claim.

FROZEN M0 DECISIONS
================================================================

1. Durable queue: SQLite-backed job table.
2. SQLite behavior: WAL mode, single writer, configured busy timeout, short transactions.
3. M1 performance fixture: deterministic local fixture sized for 100 sequential runs inside the agreed CI budget.
4. Approval mechanism: file-based, SHA-256 checksum-bound.
5. Reference validation (MVP): ownership, type validity, field existence, exact field match. Free-form semantic entailment is out of scope.
6. Secret handling: DEEPSEEK_API_KEY from environment only. Never logged, never persisted, never written to artifacts.

Queue model:

JobState: PENDING | CLAIMED | RUNNING | TERMINAL
JobTerminalReason: COMPLETED | INTERRUPTED | WORKER_ERROR
RunOutcome: VALID_COMPLETED | PRODUCT_FAILED | AUTOMATION_FAILED | INFRASTRUCTURE_FAILED | INTERRUPTED | INCONCLUSIVE

Rules:
- Job lifecycle and run outcome are separate dimensions.
- JobState=TERMINAL, JobTerminalReason=COMPLETED, RunOutcome=PRODUCT_FAILED is a successful worker execution that captured a valid product failure. It counts toward product-failure frequency.
- A worker restart converts stale CLAIMED or RUNNING jobs to TERMINAL/INTERRUPTED with RunOutcome=INTERRUPTED. Stale jobs are never silently re-run.
- Retries are new job attempts linked to the prior attempt, not mutations of history.
- Test repetition and infrastructure retry are separate counters. A product failure is never hidden by retry.

Redaction boundary:

Raw sensitive evidence may exist only in bounded process memory during collection and transformation. It must be redacted before durable persistence, provider transmission, normalized indexing, diagnostic logging, report generation, or any artifact export. Buffers are released after processing. The agent disables its own crash-dump, heap-snapshot, and verbose-log paths that would persist unredacted in-process data. OS-level paging and kernel mechanisms are documented as residual risk in the security model.

PROVIDER CONTRACT
================================================================

interface LlmProvider {
  complete(req: LlmRequest): Promise<LlmResponse>;
  capabilities(alias: ModelAlias): Promise<ModelCapabilities>;
}

type ModelAlias = "FAST_MODEL" | "REASONING_MODEL" | "FALLBACK_MODEL";

interface LlmRequest {
  alias: ModelAlias;
  system: string;
  messages: LlmMessage[];
  responseSchema?: JsonSchema;
  tools?: ToolSpec[];
  maxTokens: number;
  temperature: number;
  timeoutMs: number;
  requestId: string;
}

interface LlmResponse {
  rawText: string;
  parsed?: unknown;
  toolCalls?: ToolCall[];
  usage: { promptTokens: number; completionTokens: number; totalTokens: number };
  provider: string;
  modelId: string;
  modelVersion?: string;
  inferenceMode?: string;
  latencyMs: number;
  finishReason: string;
  warnings: string[];
}

interface ModelCapabilities {
  jsonMode: CapabilitySupport;
  toolCalls: CapabilitySupport;
  thinkingMode: CapabilitySupport;
  contextWindow: number;
  maxOutputTokens: number;
}

type CapabilitySupport = "supported" | "unsupported" | "unknown";

Rules:
- Model aliases are config-driven. Never guess. Never silently substitute.
- Do not assume the provider exposes a model catalog.
- Run bounded startup probes. Record observed behavior. Disable unsupported functionality.
- Record provider, model ID, model version, inference mode, prompt version, params, usage, latency, warnings for every call.
- Provider-specific response shapes never leak past the adapter.
- Provider unavailability must not corrupt deterministic execution evidence.
- Error taxonomy: AUTH, RATE_LIMIT, TIMEOUT, INVALID_OUTPUT, SCHEMA_MISMATCH, REFERENCE_MISMATCH, PROVIDER_UNAVAILABLE, COST_EXCEEDED.
- Retry, backoff, and circuit-breaker policy must be explicit.

JSON mode only guarantees parseable JSON where supported. It does not replace application-side schema validation.

For every AI result:
1. Parse.
2. Validate against the versioned application schema.
3. Reject unknown fields where appropriate.
4. Validate every reference against actual IDs in the input.
5. Reject unsupported actions or fabricated evidence references.
6. Attempt one bounded repair call.
7. On failure, return typed AI_INVALID_OUTPUT.
8. Never silently substitute guessed values.

================================================================
EVIDENCE REFERENCE MODEL
================================================================

Every analytical claim:

{
  "findingId": "FIND-14",
  "level": "correlated_difference",
  "statement": "...",
  "supportingEvidence": [
    { "runId": "RUN-17", "eventIds": ["EV-122"], "artifactIds": ["TRACE-17"] }
  ],
  "contradictingEvidence": [],
  "confidence": 0.89
}

Levels: observed, correlated, probable_trigger, high_confidence_trigger, confirmed_trigger, root_cause_hypothesis, confirmed_root_cause.

Reference validation confirms: investigation exists; run belongs to investigation; event belongs to run; artifact exists; artifact type is valid for the claim; cited field exists and matches; no reference to redacted or inaccessible content.

MVP scope for semantic validation: existence, ownership, type validity, field presence and match. Free-form entailment is out of scope.

Hard fail if the model claims confirmed_root_cause without approved direct evidence: source-code evidence approved by a human, instrumented state demonstrating the faulty transition, approved engineering diagnosis, or a controlled experiment proving the asserted mechanism.
