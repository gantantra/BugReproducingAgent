# Approval State Machine and Gate UX

Status: M0 frozen decision (frozen decision 4)
Package: `packages/approvals`
Schema: `schemas/approval-record.v1.json`

## Governing principle

Playwright produces evidence. Deterministic software normalizes and measures evidence. DeepSeek interprets and prioritizes evidence. Humans authorize consequential transitions.

## The three gates

| Gate | Name | What the human decides | Edit surface |
| --- | --- | --- | --- |
| 1 | `experiment_selection` | Which ranked sequences run, if any | Approve none, some, or all. Edit actions, assertions, ordering, repetitions, safety flags |
| 2 | `target_failure` | Which failure the investigation is chasing | Approve or correct the target failure signature and the run clusters |
| 3 | `final_reproduction` | Whether the minimized reproduction is the deliverable | Approve, edit, reject, or request further reduction |

## State machine, per gate per investigation

```
                            +-------------+
                            | NOT_REACHED |
                            +------+------+
                                   | proposal rendered
                                   v
                          +-------------------+
        proposal          | AWAITING_APPROVAL |<-----------+
        re-rendered  +--->+---+------+--------+            |
        (supersedes) |        |      |                     |
                     |        |      | approve (subset/all)| request_changes
                     |        |      v                     |
                     |        |   +----------+             |
                     |        |   | APPROVED |             |
                     |        |   +----------+             |
                     |        |                            |
                     |        | reject                     |
                     |        v                            |
                     |   +----------+                      |
                     +---| REJECTED |----------------------+
                         +----------+
```

- `APPROVED` and `REJECTED` are terminal for that `(gate, proposalChecksum)` pair.
- A **new proposal** for the same gate creates a new `AWAITING_APPROVAL` state bound to the new
  checksum, and marks the previous record `SUPERSEDED` in a derived view. The `ApprovalRecord`
  rows themselves are never mutated.
- `APPROVED_PARTIAL` is represented as `APPROVED` with an explicit `approvedItemIds` subset. There
  is no separate state: "approve two of five experiments" is an approval whose scope is two items.
- `request_changes` is recorded as a `REJECTED` record carrying `requestedChanges`, which the next
  `plan`/`minimize` invocation reads as input. This keeps the human intent in lineage rather than
  in a chat log.

Gate ordering is enforced: gate 2 cannot be proposed before gate 1 is `APPROVED`; gate 3 cannot be
proposed before gate 2 is `APPROVED`.

## Proposal artifacts

`investigate plan`, `investigate classify`, and `investigate minimize` each write a proposal
triple into the investigation directory:

```
investigations/INV-001/manifests/
  gate-1.experiment_selection.proposal.json     <- canonical bytes, the checksum subject
  gate-1.experiment_selection.proposal.json.sha256
  gate-1.experiment_selection.proposal.md       <- human-readable rendering
```

Canonicalisation for checksum purposes: the `.json` file is written with sorted keys, two-space
indentation, LF line endings, UTF-8 without BOM, and a trailing newline. The SHA-256 is over the
exact file bytes. The `.md` rendering is **not** part of the checksum; it is generated from the
JSON and regenerating it is safe.

The proposal is also stored via `ArtifactStore`, so its hash is independently recorded and any
later on-disk edit is detectable (`GATE_PROPOSAL_STALE`).

## Approval file

The human writes (or edits a scaffold of) a YAML file:

```yaml
schemaVersion: "1.0.0"
gate: experiment_selection
investigationId: INV-001
proposalChecksum: "sha256:3f2a9c...e41b"
decision: approve            # approve | reject | request_changes
approver:
  name: "Gantantra Agrawal"
  method: local-file
decidedAt: "2026-09-10T14:03:11Z"
approvedItemIds: [EXP-002, EXP-004]
edits:
  - itemId: EXP-002
    path: /actions/3/timeoutMs
    from: 30000
    to: 5000
    rationale: "The reported failure only appears under a short client timeout."
  - itemId: EXP-004
    path: /repetitions
    from: 20
    to: 60
    rationale: "Reported incidence is roughly 1 in 30."
safetyAcknowledgements:
  - itemId: EXP-004
    actionId: ACT-11
    classification: destructive
    acknowledged: true
    justification: "Test tenant only; data is regenerated by the fixture."
notes: "EXP-001 and EXP-003 rejected: they vary a factor the reporter says is constant."
```

`investigate approve` scaffolds this file on request (`investigate approve <gate> --scaffold`) so
the human is editing a pre-filled, schema-valid document rather than authoring YAML from scratch.
Scaffolding does not approve anything.

## Validation sequence

All seven checks must pass, in order, before any state change:

1. The approval file parses and validates against `schemas/approval-record.v1.json` with
   `additionalProperties: false`.
2. `--checksum` equals the SHA-256 of the proposal artifact bytes on disk.
3. The approval file's `proposalChecksum` equals `--checksum`. Disagreement between the flag and
   the file is `GATE_CHECKSUM_MISMATCH`; the two must agree so that neither a stale file nor a
   stale shell-history flag can approve the wrong thing.
4. The proposal artifact hash still matches its stored `ArtifactRef` (`GATE_PROPOSAL_STALE`).
5. The gate is currently `AWAITING_APPROVAL` for this investigation and this checksum.
6. Every referenced ID (`approvedItemIds`, `edits[].itemId`, cluster IDs, candidate IDs) exists and
   belongs to this investigation.
7. Every edit is inside the gate's allowed edit surface, and the edited proposal still validates
   against the proposal schema. `edits[].from` must match the current value at `path`, so an edit
   written against a different revision cannot apply silently.

Additional checks:

8. Every action classified destructive by the deterministic classifier in every approved item has a
   matching `safetyAcknowledgements` entry with `acknowledged: true`. Missing acknowledgement is
   `GATE_EDIT_OUT_OF_SURFACE`, and execution would additionally refuse with
   `EXEC_DESTRUCTIVE_BLOCKED`.
9. `decidedAt` is not in the future beyond a small skew allowance, and the resulting approval is
   within `approvals.expiryHours` when consumed.

## Allowed edit surface per gate

| Gate | Editable paths | Forbidden |
| --- | --- | --- |
| 1 | `/actions/*` (add, remove, reorder, retype within the closed set), `/assertions/*`, `/repetitions`, `/requiredEvidence`, `/safety/*`, `/timeoutMs` fields | `/experimentId`, `/hypothesis` (rejecting and re-planning is the path), any origin outside `safety.allowedOrigins` |
| 2 | `/signature/predicate` (within the deterministic predicate grammar), `/signature/label`, `/clusters/*/runIds` (reassign runs between clusters), `/clusters/*/label` | Inventing a run ID, changing a run's `RunOutcome`, changing a fingerprint |
| 3 | `/sequence/actions/*` (removal and reorder only), `/assertions/*`, `/repetitions`, `/control/*` | Adding an action absent from the pre-minimization sequence, changing the approved failure signature |

Gate 2 deserves a note: a human may correct the *predicate* that defines the target failure, but
may not overwrite deterministic measurements. Correcting "what we are chasing" is a judgement call;
rewriting "what was observed" is falsification.

## On success

In one short transaction:

1. Insert an immutable `ApprovalRecord` with `APPR-nnn`, the gate, decision, checksum, approver,
   scope, edits, acknowledgements, and the resulting `effectiveProposalChecksum` (the hash of the
   proposal after edits are applied, which is what execution consumes).
2. Store the post-edit effective proposal as its own artifact.
3. Append a lineage edge `proposed_experiment -> user_approved_experiment` (or the gate-appropriate
   edge).
4. Transition the gate state.

Execution reads the *effective* proposal, never the pre-edit one, and every run manifest records
`approvalId` and `effectiveProposalChecksum`.

## No auto-approval

There is no `--yes`, no `approvals.autoApprove`, no environment variable, and no config value that
grants an approval. The loader rejects `approvals.required` with fewer than the three gates. A test
asserts that no code path constructs an `ApprovalRecord` outside the `approve` command handler.

Non-interactive automation is supported the only safe way: a human commits an approval file, and CI
runs `investigate approve` against it. The checksum binding means that file approves exactly one
proposal and nothing else.
